# AI 性格四维与双向派生

Status: done

## Problem Statement

现有 AI 的「性格」没有唯一真源：说话方式读 `reply_mode` 与 `talkativeness`，圆桌接话读
`roundtable_chime_chance`，自己上鱼播报读 `ai_fishing_talk_*_chance`，玩家上星/上蓝反应读
`ai_catch_*_chance`，角色换目标与休息读 `ai_actor_*_chance`。这些字段分散在后台、桥接与
游戏服三处，每个都只影响一个消费点，既没有一份可验证的人格定义，也无法回答
「把这个人调得更爱凑热闹，会发生什么」。表达侧同样各写一份：普通回复与圆桌各自裁剪
人设文本，没有任何机制保证两边描述的是同一个性格版本。

后果是可复现性差：同一个角色在频道里爱接话、在自己上鱼时沉默，配置上找不到原因；
改一个数只改一个消费点，剩下几处继续按旧值走。

## Solution

把四个生活维度收敛成唯一真源，并提供两件同源产物：一份共享派生纯函数，一份同版
表达编译。

- `internal/aiconfig/personality.go`（新增）：四维定义（ID、中文标签、两端、三段行为
  约束）、单条配置的 JSON 形状与校验、共享选择器（对可行候选做 softmax 后抽样）、
  驻留底线与休整节拍公式、同版表达编译。纯函数，不读写数据库。
- `internal/store/repos_ai.go`：按 `agent_key` 读写一条 `ai_setting` JSON，带 schema、
  修订与代次；同一事务比较 `base_revision` 写新修订；软删与旧代次停用；显式非法拒绝
  保存；坏值保留并标需修复。
- `internal/aibridge/runner.go`：普通回复与圆桌都在任务开始时取一次四维快照，编译成
  四句表达约束注入 system。没有配置、配置非法或已停用时保持改造前的 system 逐字不变。
- `internal/admin/ai_settings.go`：只读聚合内部读取（定义 + 当前值 + 修订 + 派生预览），
  不新增 HTTP 路由，页面与评分入口归 T-107。

真实调度消费（游戏服与桥接的三个事件入口、配额、冷却、时限）归 T-108；本改动只保证
共享函数与表达编译本身可验证、可复用。

## User Stories

1. 作为管理员，我看到的四个旋钮与角色在游戏里说出来的话来自同一份定义：0..32 偏低、
   33..67 适中、68..100 偏高，标签与两端文案不会两处不一致。
2. 作为管理员，同一个角色在普通回复与圆桌里表现出的性格约束一致，且都标明是哪个修订。
3. 作为管理员，两个人同时调同一个角色时，后提交的一方收到「修订冲突」而不是静默覆盖
   对方刚保存的值。
4. 作为管理员，我填了 120 这样的越界值时保存会被拒绝，而不是被悄悄改成 100；库里已经
   存在的坏值不会被静默改写，读取时会告诉我要修哪一项。
5. 作为服主，升级后没有配过四维的老角色说话方式与升级前完全一致。
6. 作为服主，删掉角色后用同一个 key 新建，联系人与历史都还在，但删除前的四维不会自动
   生效；重新保存一次才绑定到当前代次。

## Implementation Decisions

- 四维与取值域：`sociability`（交往意愿）、`exploration`（尝新意愿）、`persistence`
  （持续投入）、`regularity`（作息规律），整数 0..100，缺值一律 50。定义只有
  `aiconfig.PersonalityDimensions()` 一份，界面、存储、派生与表达都从它取。
- 存储形状：`ai_setting` 键 `ai_personality:<agent_key>`，值为
  `{schema_version, revision, generation, sociability, exploration, persistence, regularity}`。
  不新增表、不新增迁移；派生行为与派生表达都不落库，保存路径只有
  `store.AISavePersonality` 一处。
- 修订与并发：`AISavePersonality` 在单个事务里读当前修订、比对 `base_revision`、
  写 `revision+1` 并绑定 `ai_runtime_control` 的当前代次。不一致返回
  `ErrAIPersonalityConflict`，库里一个字都不改。保存要求 `schema_version` 显式等于
  当前版本；未知版本拒绝，不静默改写成当前版本后落库。读侧报出的「可提交修订」与
  写侧比较口径共用 `PersonalityRevisionOf`：坏记录只要修订号还读得出，就用读到的那个
  修订来修复，不必按 0 重来。
- 停用：读取时一并取 `deleted_ts` 与 `tombstoned`/`generation`。已删除或属旧代次的
  配置 `Derivable()` 为假：不参与派生、不参与表达编译，但存值保留供重新确认。
  同 key 恢复后旧代次不自动生效，保存一次即重新绑定当前代次。
- 校验：七个字段（`schema_version`、`revision`、`generation` 与四维）必须齐全且都是
  整数；缺字段、`null`、小数、字符串都算显式非法，不能被当成合法的 0。超域取值、
  未知 `schema_version`、坏 JSON 同理。保存返回 `ErrAIPersonalityInvalid`（不 clamp）；
  读取返回 `NeedsRepair` 与原因，并原样保留存值。
- 共享派生：`z=Σ(2x−1)·f/2`（x=值/100，f 为候选的四项语义特征，各 0..1），
  只在可行候选上做 `softmax(z)`；候选按 ID 稳定排序后单次抽样，种子决定唯一结果；
  不可行候选得分与权重恒为 0；没有可行候选返回无动作；重复 ID 视为调用方错误。
  沉默与维持作为普通候选参与比较，靠「只有它可行」得到必静默。
- 时间：`Dmin=Bhard+Bextra·p·(0.5+0.5r)`、`Trest=Tbase·(1+0.5r)`。`Bhard`/`Bextra`/
  `Tbase` 是类型级参数，没有每角色覆盖；预览从现有
  `ai_actor_fishing_session_min_s` / `ai_actor_fishing_session_max_s` / `ai_actor_rest_min_s`
  继承，不新增、不修改任何时长真源。
- 表达编译：`CompilePersonalityExpression` 拼四条「维度 值/100（分段）：行为解释」并带
  `schema vN · 修订 M`，末尾声明人设描述只提供背景与口癖。缺值不编译（中性即不加约束），
  非法或停用不编译——这样关掉派生就回到原表达。
- 边界：不接新活动、不做评分 UI、不改官方协议、结算、玩家状态条、静态库与 CI；
  旧 `reply_mode`/`talkativeness` 与各旧概率一律不是派生输入。

## Testing Decisions

- 定义层（`internal/aiconfig`）：四维定义唯一且固定（多一维/改 ID 即红）；JSON 字段集
  恰好七个（多出「外向度」或第二组权重即红）；分段端点 0/32/33/67/68/100；表达与行为
  返回同一 `schema`/修订；同输入同种子结果一致且逆序候选一致；不可行候选权重 0；
  只有静默可行时必静默；空集与重复 ID 拒绝；三类事件（圆桌、玩家星蓝反应、自己渔获
  播报）权重都归一；低/高端点与「高交往+高投入」组合可表达；`p` 单调不降低底线；
  `r` 只放大或持平休整间隔；特征结构反射断言只有四项 float64。
- 存储层（真实 SQLite）：缺值为中性；首存修订 1 且绑定代次；非法值不落库；修订冲突
  不覆盖先到的值；坏值保留并可显式修复；软删停用但存值仍在；同 key 恢复沿用联系人
  UID、战绩与旧回复且旧代次不自动生效；旧行为字段与旧概率改变后四维不变。
- 配置边界（补验）：缺任一必需字段、非整数取值（小数/字符串/`null`）逐项报需修复并
  停用派生，原值仍可查；显式 0 合法、缺键仍是中性 50；未知 `schema_version=2` 保存
  被拒且无任何写入；坏记录的读侧修订可直接用于修复，陈旧修订被拒且原值不变。
- 后台内部读取（真实 SQLite）：一次读取同时给出定义、当前值、修订与派生预览；预览与
  纯函数同版同值；非法与已删除如实显示为「需修复」「已停用」；派生参数继承现有活动
  时长配置（上限小于下限时按下限）；旧概率不影响预览。
- 桥接表达（真实 SQLite）：普通回复（600 字人设）与圆桌（400 字人设）得到同一修订的
  同一段约束；缺值时 system 与 `trimToTokens(prompt, 600)` 逐字相同；非法值停止编译；
  任务开始取的快照不随后台保存变化，下一任务才见新修订；旧概率不影响表达；静态断言
  两处调用都走 `expressionsLine`，退回旧人设裁剪即失败。
- 反证：把桥接改回旧人设裁剪、把 `p` 从底线公式里去掉、给候选加第五个特征字段，
  都会让上述用例变红（实测见执行回执 §4）。

## Out of Scope

- 真实调度消费：游戏服与桥接的三个事件入口、配额、冷却、时限及其状态投影归 T-108。
- 管理页面、评分按钮、草稿/撤销与任何 HTTP 契约扩展归 T-107。
- 不新增表、迁移或依赖；不改官方协议形状、结算、玩家状态条、静态库与 CI。
- 不迁移、不折算旧 `reply_mode`/`talkativeness` 与各旧概率；既有值原样封存，由后续票处置。
- 不实现玩家侧入口（DEV-109：玩家只游玩，旋钮只由管理员调）。
