# ADR 0002：AI 迁移使用临时号段 00900+

Status: accepted

## Context

本仓库的官方迁移号从 `00001` 起连续分配，官方 main 当前已用到 `00062`（最大号仍会随官方前进）。
`internal/store/store.go` 的迁移器按**文件名排序**执行，并以**编号**作为 `schema_migrations`
的主键；AI 分支早期把五条 AI 迁移放在 `00060`/`00061`/`00078`–`00080`，与官方号段重叠。
只要官方继续在 `00001`–`00899` 内取号，AI 分支每次跟随官方都要重新让号、回归与复验，
这是持续成本。而 `retireStaleMigrationRows` 只能退役「文件名已不在迁移目录」的旧行，
救不了仍在目录里的同号文件。

## Decision

1. **官方号段 `00001`–`00899` 归官方**，AI 分支一律不取。
2. **AI 迁移临时独占 `00900`+**，从 `00900` 起连续分配，并保持依赖序
   （建表 → 清理 → 订阅 → 全局范围 → 加列）。当前五条：
   `00900_ai_bridge.sql`、`00901_ai_cleanup_legacy.sql`、`00902_ai_map_subscription.sql`、
   `00903_ai_global_scope.sql`、`00904_ai_fishing_talk.sql`。
3. **这是临时方案**：等官方给出 mod 迁移号段规范（或出现等价新解法）后，一次性把 AI 迁移
   对齐到该规范；在那之前不反复讨论号段本身，也不为每次官方取号重新让号。
4. 官方退役段 `9_000_000+version` 与 `00900`+ 数量级不同，不会冲突。

## Consequences

- AI 迁移现在排在官方全部现有迁移之后（字典序 `00900` > `00062`），不再与官方抢号；
  官方要占到 `00900` 需新增约 838 个迁移，实际不可达。
- 旧库升级依赖官方既有 `retireStaleMigrationRows`：旧的 `00060_*`/`00061_*` 登记行会被退役到
  `9000060`/`9000061`，与既有合并目录行为一致；本 ADR 不改变该算法。
- 号段是临时约定，不是官方契约。**不得**把 `00900`+ 写进 `specs/capabilities/` 当成永久能力，
  也不得据此推断官方已支持 mod 迁移号段。
- 官方给出 mod 号段规范后需要一次迁移（含旧库登记行处理），届时另开票评估，不在本 ADR 内预设计。
